# AWS 부하 테스트 환경 구성

부하 테스트를 실행한 AWS 환경의 **구성 기록**이다. 실행 방법과 측정 기준은
[`load-test-scenario.md`](./load-test-scenario.md)에 있고, 이 문서는 **무엇을 어떻게 배치했는가**만 다룬다.

## 1. 인스턴스 3대

```
[k6]  172.31.47.74
   │  부하 발생
   ▼
[앱]  172.31.43.201 : 8080
   │  MySQL · Redis · Kafka
   ▼
[인프라] 172.31.40.51 : 3306 · 6379 · 9092
```

| 역할 | Name | 유형 | 사설 IP |
| --- | --- | --- | --- |
| 인프라 (MySQL · Redis · Kafka) | `petcoupon-performance-test` | m5.xlarge (4 vCPU / 16GB) | `172.31.40.51` |
| 앱 (Spring Boot) | `petcoupon-k6-generator` | c5.xlarge (4 vCPU / 8GB) | `172.31.43.201` |
| k6 (부하 발생기) | `petcoupon-k6` | r5.xlarge (4 vCPU / 32GB) | `172.31.47.74` |

셋 다 기본 VPC · **같은 AZ(`ap-northeast-2c`)** 에 둔다. AZ 가 다르면 그만큼 네트워크 지연이
붙어서 응답 시간에 섞인다(시나리오 §2).

> ⚠️ **Name 태그가 역할과 어긋나 있다.** 원래 2대(앱+인프라 한 대, k6 한 대)로 쓰던 인스턴스를
> 재사용하면서 역할만 바꿨기 때문이다. `petcoupon-k6-generator` 는 지금 **앱 서버**다.
> 이 문서와 아래 보안 그룹 설명은 **역할 기준**으로 읽는다.

### 왜 앱과 인프라를 나눴나

한 대에 올리면 병목이 앱인지 MySQL·Redis·Kafka인지 구분되지 않는다. MySQL 이 CPU 를 먹어서
느려진 것과 앱이 느린 것을 같은 수치로 보게 된다.

### 왜 k6 기기가 가장 큰가

k6 는 **VU 하나당 메모리 1~5MB** 를 쓴다. 3단계 목표가 20,000 VU 라 최소 20GB 부터 필요해서,
앱(8GB)이나 인프라(16GB)보다 큰 메모리 인스턴스를 배정했다. CPU 보다 메모리가 병목이라
c 계열이 아니라 r 계열이다.

실제 필요량은 2단계(10,000 VU)에서 `free -m` 으로 재고 3단계 전에 확정한다. 모자라면 인스턴스를
중지하고 유형만 올리거나(중지 상태에서 변경 가능), `INSTANCE_INDEX` · `INSTANCE_STRIDE` 로
여러 대에 나눠 쏜다(`README.md` "여러 대에서 나눠 쏠 때").

### 앱 서버 기동

사설 IP 는 환경변수로 주입한다. 앱은 소스를 두지 않고 **빌드한 jar 만 올려서** 실행한다.

```bash
# 앱 서버(172.31.43.201)
ulimit -n 65535

TZ=Asia/Seoul \
DB_URL="jdbc:mysql://172.31.40.51:3306/petcoupon" \
REDIS_HOST=172.31.40.51 \
KAFKA_BOOTSTRAP_SERVERS=172.31.40.51:9092 \
java -jar app.jar
```

부하 측정 시에는 여기에 튜닝 환경변수(`ISSUE_LOG_LEVEL` · `TOMCAT_*` · `DB_POOL_SIZE` ·
`COUPON_RECONCILIATION_SCHEDULER_ENABLED`)를 함께 준다. 값과 근거는
[`load-test-scenario.md`](./load-test-scenario.md) §2 사전 설정에 있다.

> ⚠️ **`TZ` 를 빼면 안 된다.** EC2 는 기본이 UTC 라 OS 시간대를 맞춰두지 않으면 앱만 UTC 로
> 돌아간다. 쿠폰 생성 스크립트는 인프라 서버(KST)에서 실행되므로 발급 시작 시각이 **9시간
> 어긋나** 쿠폰이 열리지 않는다. OS 설정에 기대지 않고 실행 명령에 명시한다.
>
> `ulimit -n` 은 셸 세션 단위라 SSH 를 새로 붙을 때마다 다시 지정해야 한다.
> `TOMCAT_MAX_CONNECTIONS=25000` 을 받으려면 파일 디스크립터가 그만큼 필요하다.

## 2. 보안 그룹

그룹은 두 개이고, **앱과 k6 가 같은 그룹에 들어 있다.**

| 그룹 | 소속 인스턴스 |
| --- | --- |
| `petcoupon-test-sg` | 인프라 |
| `petcoupon-k6-sg` | **앱 + k6** |

> ⚠️ **그룹 이름도 역할과 반대다.** `test-sg` 가 인프라이고, `k6-sg` 안에 앱이 있다.
> 보안 그룹 이름은 생성 후 변경할 수 없으므로, 각 규칙의 **설명(Description)에 역할을 적어** 둔다.

### 인바운드 규칙

**`petcoupon-k6-sg`** (앱 + k6)

| 포트 | 원본 | 용도 |
| --- | --- | --- |
| `8080` | `petcoupon-k6-sg` (자기 자신) | k6 → 앱 |
| `8080` | `petcoupon-test-sg` | 인프라 → 앱 (관리자 API·쿠폰 생성 스크립트) |
| `8080` | `<작업자 IP>/32` | 대시보드 확인 |
| `22` | `<작업자 IP>/32` | SSH |

**`petcoupon-test-sg`** (인프라)

| 포트 | 원본 | 용도 |
| --- | --- | --- |
| `3306` | `petcoupon-k6-sg` | 앱 → MySQL |
| `6379` | `petcoupon-k6-sg` | 앱 → Redis |
| `9092` | `petcoupon-k6-sg` | 앱 → Kafka |
| `22` | `<작업자 IP>/32` | SSH |

아웃바운드는 기본값(전체 허용)을 그대로 둔다.

### 원본에 IP 대신 보안 그룹을 쓰는 이유

사설 IP 를 직접 적어도 동작하지만, 그룹을 지정하면 **인스턴스를 다시 만들어 IP 가 바뀌어도
규칙이 깨지지 않는다.** 세 개를 손으로 입력하다 오타를 내는 사고도 없앤다.

앱과 k6 가 같은 그룹이라 `8080 ← 자기 자신` 한 줄로 k6 → 앱 이 열린다.

### 인프라 → 앱 8080 이 필요한 이유

쿠폰 생성 스크립트(`setup-demo-coupon.sh`)가 **인프라 서버에서 실행되면서 앱의 관리자 API 를
호출한다.** MySQL 컨테이너를 `docker exec` 로 직접 읽는 부분이 있어 인프라에서 돌려야 하는데,
API 대상은 앱이다. 이 규칙이 없으면 스크립트가 2분쯤 매달렸다가 연결 타임아웃으로 끝난다.

> 규칙의 **설명(Description) 칸은 한글을 받지 않는다.** 영문·숫자와 일부 기호만 허용되며
> (`a-zA-Z0-9 ._-:/()#,@[]+=&;{}!$*`), 한글이나 `→` 를 넣으면 저장이 통째로 롤백된다.
> `app to mysql` 처럼 적는다.
