# 부하 테스트 결과

시나리오와 판정 기준은 [`load-test-scenario.md`](./load-test-scenario.md), 실행 환경 구성은
[`aws-setup.md`](./aws-setup.md)에 있다. 이 문서는 **실측값과 그 해석**만 담는다.

측정일 2026-08-30 · AWS EC2 3대 분리 구성(`ap-northeast-2c`)

## 0. 결론

**핵심 정합성은 1~3단계 11회차 전부 통과했다.** 다만 접수 응답 p95·p99 는 시나리오 §5.2 의
실패 판정선(3초)을 대부분의 회차에서 넘겼다. 두 가지를 나눠서 읽어야 한다.

| 구분 | 결과 |
| --- | --- |
| **정합성** | ✅ **전 회차 통과** — 초과 발급·중복 발급·순번 충돌·DLQ·접수 실패 0건 |
| **성능** | ✗ 접수 응답 p95·p99 목표(500ms · 1초)·실패 판정선(3초) 미충족 |

### 정합성 판정

| 판정 항목 | 결과 |
| --- | --- |
| 초과 발급 | **0건** (11회차 전체) |
| 중복 발급 (1인 2매) | **0명** |
| 순번 정합성 | 매 회차 1~N 빠짐·중복 없음 |
| 재고 정합성 | Redis 잔여 = DB 잔여 = 0 |
| 꼬리 유실 | Redis 순번 = DB 최대순번 |
| DLQ | **0건** |
| 접수 실패 | **0건** (5xx · 4xx 모두 0) |

⚠️ **단, `issue_message` 가 `SENT` 로 남은 회차가 3건 있다.** 이 상태로는
`verify_issue_result.sql` 10번 항목(미처리 Outbox)이 **FAIL** 이다 — 아래 "수동 개입" 참고.

### 성능 판정

| 지표 | 시나리오 §5.2 기준 | 3단계 실측 | 판정 |
| --- | --- | --- | --- |
| 접수 응답 p95 | 목표 500ms · **실패 3초 초과** | 15.02~17.59초 | ✗ |
| 접수 응답 p99 | 목표 1초 이내 | 15.65~18.25초 | ✗ |
| 에러율 | 1% 미만 | 0% | ✅ |
| 타임아웃 | 0건 | 0건 | ✅ |
| 전건 확정 소요 | 5분 내 | 215~224초 | ✅ |
| 전체 실행 시간 | 5분 이내 | 18.8~20.4초 | ✅ |

p95 미충족은 **처리가 느린 것이 아니라 한 대에 동시 요청이 몰린 큐 대기**다. 20,000건을
1,030 TPS 로 소화하면 19,000번째 요청은 산술적으로 18.4초를 기다린다. 현재 처리량만 기준으로
단순 계산하면 3초 이내 처리를 위해 약 7배의 처리 용량이 필요하다. 다만 인프라 노드(4 vCPU)의
CPU가 이미 100%에 도달했으므로, 앱 수평 확장에 따른 실제 개선 폭은 별도 실측이 필요하다.

시나리오 §5.2 는 이 기준에 대해 "이전 실험의 p95 3초 기준은 동기 DB 저장을 포함한 구조의
값이므로, 현재 구조에서는 비교용 참고치로만 사용한다"고 단서를 달고 있다. 표의 실패 판정과
이 문장이 서로 엇갈리므로, **기준 자체를 정리하는 것을 후속 과제로 둔다.**

### 수동 개입 기록

2단계 2회차, 3단계 2·5회차에서 `issue_message` 1건이 `CONSUMED` 로 넘어가지 못하고 `SENT` 로
남았다(§8.1 의 경쟁 상태). 이 상태에서는 두 가지가 막힌다.

| | 원본 상태 | 수동 개입 후 |
| --- | --- | --- |
| `verify_issue_result.sql` 10번 (미처리 Outbox) | **FAIL** (1건) | PASS |
| 초기화 API | `COUPON409-8` 로 거절 | 정상 |

다음 회차를 진행하려면 초기화가 필요해서, 해당 행의 status 를 손으로 `CONSUMED` 로 바꿨다.

```sql
UPDATE issue_message SET status='CONSUMED' WHERE coupon_id=1 AND status='SENT';
```

**이 문서의 "미처리 0건"은 수동 개입 후 값이다.** 발급 데이터 자체는 개입 전후가 동일했고
(해당 건도 `coupon_issue` 에 `ISSUED` 로 존재), 초과 발급·중복 발급·순번은 원본 상태에서도
전부 정상이었다. 즉 **핵심 발급 정합성은 정상이고, 파이프라인이 자연 소진되지 않은 것이 결함**이다.

### 범위와 미수집 지표

프로젝트 목표 규모인 **3단계(동시 20,000명 · 경쟁률 2:1)** 에서 접수 성공률 100%,
처리량 1,030/s, 확정 220초를 기록했다. 4단계(50,000 VU)는 시나리오 §3 이 "여유 시"로
둔 보강 검증이라 이번 범위에서 제외했다.

측정 과정에서 결함 2건을 발견했다 — §10 참고(#208 · #210).
확정 지연을 줄이려는 가설(Stream `batchSize` 확대)은 실험으로 기각했다 — §6 참고.

시나리오 §5.3 이 요구하는 자원 지표(Consumer Lag, HikariCP, Tomcat, CPU · 메모리)는
§4 회차에서 수집하지 않았다. **결함 수정 후 재검증 3회차(§5)에서 별도로 측정해 채웠다.**

### 측정 조건 한 가지

**발급 이력 300만 건 더미데이터는 이번 AWS DB 에 적재하지 않았다.** 회원 100만 명만 넣었다.
이번 측정 목표는 §1 의 정합성이고, 다른 쿠폰의 발급 이력은 초과 발급·중복 발급·순번 충돌에
영향을 주지 않는다. 대량 데이터 상태에서의 발급·조회·배치는 로컬에서 이미 검증했다
(`integration-test-result.md` TC-80~85).

⚠️ 다만 시나리오 §9 선행 조건 표는 이 항목을 `✅` 로 두고 있어 **이번 실행 조건과 어긋난다.**
시나리오 문서 정정은 별도 이슈로 뺀다.

시나리오 §7 이 경고한 "회차 간 초기화 지연"(발급 50만 + 이력 65만 삭제에 470초)은
이번 조건에서 해당되지 않았다. 더미데이터가 없을 때 **2.4초**, 시연 준비로 SEED 300만 건을
적재한 뒤에도 **0.035초**였다. 삭제 대상이 부하 테스트 쿠폰 한 개로 한정되면 다른 쿠폰의
발급 이력이 아무리 많아도 영향이 없다 — §7 경고는 **한 쿠폰에 50만 건이 쌓였을 때**의 값이다.

## 5. 결함 수정 후 재검증 — 20,000 VU / 재고 10,000 · 3회

§8 의 결함 2건을 수정한 뒤(#208 · #210) 같은 조건으로 3회 더 돌렸다. **§4 와는 앱 버전이
다르므로 같은 표에 넣지 않는다.** 목적은 두 가지다.

- `markSent` 수정이 실환경에서 동작하는지 — `SENT` 잔존이 사라지는가
- 시나리오 §5.3 이 요구하는 자원 지표 수집

| 회차 | 소요 | 처리량 | 평균 | p95 | 접수 성공률 | 5xx | 확정 소요 | 수집 방식 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 36.6초 | 547/s | 18.88s | 29.60s | 100% | 0 | 242초 | Kafka CLI 2초 |
| 2 | 23.3초 | 859/s | 10.82s | 19.58s | 100% | 0 | 226초 | Kafka CLI 5초 |

### 수집 스크립트가 인프라에 부하를 줬다

1·2회차가 §4(981~1,064/s)보다 느린 것은 **수집 방식 때문이었다.**
`kafka-consumer-groups.sh` 는 호출할 때마다 JVM 을 새로 띄우는데, 이를 인프라 서버에서
2~5초마다 부르니 **부하가 없는 상태에서도 인프라 CPU 가 100% 로 올라갔다.**

3회차에서는 Kafka CLI 대신 `issue_message.status = 'SENT'` 백로그를 애플리케이션 관점의
미확정 메시지 대체 지표로 수집했다. MySQL 조회 한 번으로 바꾸자 **§4 수준으로 복귀했다.**
Kafka Consumer Lag은 Kafka offset 차이이고 `SENT`는 DB의 메시지 상태이므로 동일한 지표는 아니다.

자원 지표를 수집하려던 스크립트가 오히려 측정 대상에 부하를 더했다.
아래 자원 지표는 전부 **3회차(수집 부하가 없는 회차)** 값이다.

(#208), 이 3회차는 실환경에서 회귀가 없음을 확인한 것이다.

### 시스템 자원 (시나리오 §5.3)

3회차 기준. 접수 구간(20초)과 확정 구간(216초)을 5초 간격으로 샘플링했다.

| 출처 | 지표 | 최대 |
| --- | --- | --- |
| Actuator | `hikaricp.connections.active` | **299 / 300** |
| Actuator | **`hikaricp.connections.pending`** | **234** |
| Actuator | `tomcat.threads.busy` | 373 / 400 |
| Actuator | `process.cpu.usage` (앱) | 71% |
| EC2 (앱) | — | 위와 동일 |
| EC2 (인프라) | CPU | **100%** |
| EC2 (인프라) | 메모리 | 2.0GB / 15.6GB |
| DB | `SENT` 백로그(Consumer Lag 대체 관측 지표) | 4,558 |

**병목은 앱이 아니라 인프라다.** 앱 CPU 는 71% 로 여유가 있는데 MySQL · Redis · Kafka 를
한 대(4 vCPU)에 올린 인프라가 100% 로 포화됐다. §0 에서 "앱을 늘려도 인프라가 먼저 병목이
된다"고 적은 근거가 이 값이다.

⚠️ **`pending` 이 0 이 아니다.** 시나리오 §2 는 "`pending` 이 0 을 유지하는 선까지 풀을
올린다"고 했는데, 풀 300 으로도 접수 순간 234 개가 커넥션을 기다렸다. 다만 대기 시간이
30초 타임아웃 안이라 **5xx 는 0건**이었다 — 풀 100 일 때(§6)와 달리 포화는 됐으나
무너지지는 않았다. 이 규모에서 `pending 0` 을 만들려면 풀을 더 올려야 하는데,
인프라가 이미 CPU 100% 라 **커넥션을 늘려도 처리량이 따라오지 않는다.**

측정 중 샘플러 자체가 24초간 멈춘 구간이 있었다 — 접수 순간 Actuator 응답이 느려져
수집 루프가 밀린 것으로, 앱이 포화됐다는 방증이다.

## 6. Stream Consumer batch size 실험 — 가설 기각

확정이 접수보다 20배 느린 원인(§8)을 좁히기 위해, Redis Stream Consumer 의
`XREADGROUP COUNT` 값을 바꿔가며 확정 시간을 비교했다. 이 값은 코드에 `10` 으로 박혀 있던 것을
설정으로 뺐다(#212).

**가설**: 한 번에 10건씩만 읽어오니 20,000건이면 2,000번 왕복한다. 값을 키우면 왕복이 줄어
확정이 빨라질 것이다.

| `batchSize` | 접수 소요 | 처리량 | 확정 소요 |
| --- | --- | --- | --- |
| **10** (기본) | 20.0초 | 1,002/s | **216초** |
| **50** | 20.3초 | 988/s | **218초** |
| **200** | 20.8초 | 963/s | **219초** |

**20배를 키워도 확정 시간이 변하지 않았다.** 216 → 218 → 219초는 측정 편차(§4·§5 에서
215~242초) 안이다. **가설을 기각한다.**

각 값마다 2회씩 돌리고 **2회차만 비교**했다. 앱을 재기동하면 첫 회차는 항상 접수 36초 안팎 ·
540 TPS 대로 나온다(§5 1회차와 동일한 패턴) — 워밍업이라 값 비교에 쓸 수 없다.

### 왜 안 빨라졌나

`batchSize` 는 **메시지 병렬 처리 개수가 아니라 Redis 조회 명령의 COUNT** 다(#212 PR 설명).
한 번에 200건을 읽어와도 처리는 단일 폴링 루프가 순차로 한다.
`StreamMessageListenerContainer` 에 executor 를 주지 않아 구독당 스레드가 하나다.

즉 **병목은 Redis 왕복 횟수가 아니라 읽어온 뒤의 순차 처리**다.

### 확정 구간에는 자원 여유가 있다

§5 에서 잰 인프라 CPU 를 구간별로 나눠 보면 분명하다.

| 구간 | 인프라 CPU | 성격 |
| --- | --- | --- |
| 접수 (20초) | **98~100%** | 자원 한계 |
| 확정 (216초) | **평균 46%** (35~50% 대) | **구조 한계** |

확정 구간에서 Redis 재고가 8,227 → 0 으로 92초에 걸쳐 **초당 약 89건씩 거의 일정하게** 줄었다.
자원이 부족하면 들쭉날쭉하거나 점점 느려지는데, 일정하다는 것은 처리 능력의 상한에 걸려 있다는 뜻이다.

**접수와 확정의 병목이 서로 다르다.** 접수는 자원(인프라 CPU 100%)이고, 확정은 구조(단일 스레드)다.
그래서 확정을 줄이려고 인프라를 키우는 것은 효과가 없다 — 자원이 절반 넘게 남는다.

### 다음 개선 방향

| 후보 | 예상 효과 | 검토할 점 |
| --- | --- | --- |
| **Stream Consumer 병렬화** | 스레드 수만큼 배수 — 가장 큼 | 순번 발급은 Lua 가 원자적이라 중복·누락은 없으나, DB 삽입 순서 보장이 달라진다 |
| Outbox INSERT 배치화 | 건당 DB 왕복 감소 | 코드 변경 범위가 큼 |
| Kafka 파티션 분산 | Stream 을 푼 뒤에야 의미 | 파티션 키가 `couponId` 라 쿠폰 1개 부하에서는 3개 중 1개만 동작 |
| 인프라 증설 | **없음** | 확정 구간 CPU 46% — 이미 여유 |

Stream 이 파이프라인 맨 앞이라 여기가 초당 89건만 내보내면 뒤를 늘려도 소용없다.
**Stream 병렬화가 먼저**다. 다만 순서 보장을 건드리는 변경이라 별도 이슈에서 정합성 검증과 함께 다룬다.

## 7. 적정 풀 크기를 찾은 과정

1단계 첫 실행은 두 번 실패했다. 둘 다 **정합성이 아니라 처리 용량 문제**였고, 실패한 회차에서도
초과 발급·중복 발급·순번 충돌은 0건이었다.

| 시도 | 조건 | 결과 |
| --- | --- | --- |
| 무효 1 | MySQL `max_connections` **151** | 접수 성공률 **31.9%**, 5xx 1,560건 |
| 무효 2 | 풀 100 · 스레드 2,000 | 접수 성공률 **31.9%**, 5xx 1,159건 |
| 정식 | **풀 300 · 스레드 400** | 접수 성공률 **100%**, 5xx 0건 |

### 무효 1 — 인프라 설정이 이전 세대였다

부하 서버의 `docker-compose.yml` 이 이전 실험(PoC) 시절 파일이어서 `--max-connections=500` 이
빠져 있었고 MySQL 기본값 151로 떠 있었다. Redis 의 `maxmemory-policy noeviction` ·
`appendonly` 도 함께 빠져 있었는데, 이는 **재고 키가 축출되면 재고가 남았는데도 품절로
처리되는** 정합성 위험이라 더 중요했다. 레포의 파일로 교체해 해결했다.

### 무효 2 — 풀 100 이 부족했다

로컬 200 VU 에서는 풀 100 으로 충분했으나(`integration-test-result.md` §1), AWS 2,000 VU 에서는
같은 값이 무너졌다. HikariCP 지표가 원인을 정확히 가리켰다.

```
Connection is not available, request timed out after 30000ms
(total=100, active=100, idle=0, waiting=113)

hikaricp.connections.usage     11,139회 / 6.26초   → 평균 0.56ms, 최대 10ms
hikaricp.connections.acquire   12,191회 / 49,463초 → 평균 4.06초, 최대 30.01초
hikaricp.connections.timeout   1,210건
```

**쿼리 자체는 0.56ms 로 빠르고, 대기 시간만 7,000배 길었다.** 병목은 DB 가 아니라 풀 앞의
대기열이었다. MySQL 은 500 까지 받을 수 있는데 앱이 104 개만 쓰고 있었다는 점도 같은 결론을
가리킨다.

스레드를 2,000 에서 400 으로 **낮춘** 것도 함께 효과가 있었다. 앱 서버가 4 vCPU 인데 2,000 개
스레드를 돌리면 컨텍스트 스위칭 비용이 처리 시간을 잠식한다. 0.56ms 짜리 작업에는 400 개로도
초당 수만 건을 낼 수 있다.

## 8. 접수와 확정의 처리량 차이

2단계에서 드러난 구조적 특성이다.

```
접수  965 TPS   10,000건 / 10.4초
확정   45 TPS    5,000건 / 112초
```

접수는 요청을 Redis Stream에 적재한 뒤 202를 반환하므로 빠르다. 이후 Stream Consumer가
Redis Lua로 재고를 선점하고 Outbox를 저장하며, `Outbox → Kafka → Consumer → MySQL`을 거쳐
최종 확정된다. **설계상 의도된 차이**이며, 사용자가 체감하는 것은 접수 응답이다.

다만 3단계는 재고가 10,000 이라 확정에 **약 220초**가 예상된다. §5.2 의 실패 판정 기준인
300초 타임아웃까지 여유가 크지 않다.

확정이 느린 원인은 §6 에서 좁혔다 — Redis 왕복 횟수가 아니라 Stream Consumer 의 단일 스레드
순차 처리이며, 확정 구간 인프라 CPU 는 46% 로 자원 여유가 있다.

## 10. 측정 중 발견한 결함

### 10.1 `markSent` 가 `CONSUMED` 를 덮어쓰는 경쟁 상태 (#208)

2단계 2회차에서 `issue_message` 1건이 `CONSUMED` 가 아닌 `SENT` 로 남았다.
**발급 데이터 자체는 완전하다** — `coupon_issue` 5,000건 전부 `ISSUED`, 순번 1~5,000 연속,
빠진 순번 0개다. 해당 건(순번 49, `user_id` 82)도 쿠폰 행이 정상 존재한다.

원인은 두 UPDATE 가 **모두 조건 없이** 같은 행을 덮어쓰는 데 있다.

```
발행기   markSent()      SET status = SENT      WHERE message_id = :id
Consumer markConsumed()  SET status = CONSUMED  WHERE topic + message_key
```

정상 순서는 `SENT → CONSUMED` 지만, Kafka 가 같은 VPC 내부라 지연이 1ms 미만이어서
Consumer 가 먼저 끝나는 경우가 생긴다. 그러면 발행기의 `SENT` 가 나중에 커밋되며
`CONSUMED` 를 되돌린다.

```
issue_message.processed_at   02:20:18.257   markSent 가 찍은 시각
coupon_issue.created_at      02:20:18.263   6ms 뒤 — Consumer 가 쿠폰 생성
최종 status                   SENT           나중에 쓴 쪽이 이김
```

두 UPDATE 모두 정상 성공이라 **예외도 로그도 남지 않는다.** 앱 로그에 ERROR 가 한 줄도 없었다.

| 영향 | |
| --- | --- |
| 정합성 | 없음 — 초과 발급·중복 발급·순번 모두 정상 |
| 성능 측정 | 없음 |
| 실제 문제 | 장부상 미소진으로 남아 **정합성 검증 배치와 대시보드 검증 버튼이 막힌다** |

수정 방향은 `markSent` 에 조건을 거는 것이다. `CONSUMED` 는 종착 상태라 `SENT` 로
되돌아갈 이유가 없다.

```sql
WHERE im.messageId = :messageId AND im.status <> 'CONSUMED'
```

같은 종류의 레이스를 조건부 UPDATE 로 막은 선례가 이미 레포에 있다 —
`IdempotencyKeyRepository` 의 `provisional` 분기 주석 참고.

**발생 빈도**: 발급 68,000건 중 **3건** (약 0.004%) — 2단계 2회차, 3단계 2·5회차.
타임스탬프를 확인한 두 건 모두 `markSent` 와 Consumer 의 시간차가 3~6ms 였다. 3단계 2회차는 **순번 1번**,
즉 부하 시작 직후 첫 요청에서 발생해 발행기와 Consumer 가 가장 치열하게 겹치는 순간임을 보여준다.

**초기화까지 막는다.** `POST /internal/coupons/{id}/reset` 이 `COUPON409-8`
("앞 회차 메시지가 아직 처리 중이라 초기화할 수 없습니다")로 거절해, 다음 회차를 진행하려면
해당 행의 status 를 손으로 `CONSUMED` 로 바꿔야 했다. 회차를 반복하는 측정에서는 이 점이
가장 실질적인 지장이다.

**수정 결과 (#208)**: `markSent` 에 `NOT IN (CONSUMED, ABANDONED)` 가드를 넣었다.
수정 후 3회차(발급 30,000건)에서 `SENT` 잔존 0건, 초기화 API 도 매번 바로 통과했다 — §5 참고.
DLQ 는 일부러 막지 않았다. `claimForReprocess` 가 status 를 DLQ 로 둔 채 재처리를 선점하므로,
관리자 재처리로 재발행에 성공한 건은 DLQ → SENT 로 올라가야 한다.

### 10.2 부하 테스트 현황 API 의 `passed` 가 재고 통과 수가 아님 (#210)

대시보드 깔때기에서 "재고 통과" 막대가 "Kafka 발행"보다 아래로 내려가, 상류 단계가 하류보다
작아 보이는 역전이 나타난다.

`CouponLoadTestStatusServiceImpl` 의 `passed` 가 `coupon_issue` 를 세기 때문이다.
`coupon_issue` 행은 파이프라인 맨 끝에서 생기므로, 이 값은 **재고 통과 수가 아니라 DB 확정 수**다.
같은 이유로 "DB 확정" 막대와 값이 사실상 겹친다.

Redis Lua 가 실제로 통과시킨 건수는 Redis 에만 있다.

```
totalQuantity - Redis 재고  =  진짜 재고 통과 수
```

이 시스템에서 가장 보여줄 만한 것이 **Redis Lua 의 원자적 차감**("2,000명이 동시에 왔는데
정확히 1,000명만 통과")인데, 지금은 그 자리가 비어 있다. 시연 영상 이전에 고치는 것이 좋다.

⚠️ 단 `passed` 는 초과 발급 판정(`overIssued`)에도 쓰인다. 그 판정은 `verify_issue_result.sql`
과 기준이 같아야 하므로 **`coupon_issue` 기준을 유지**하고, 깔때기용 값을 따로 추가해야 한다.
