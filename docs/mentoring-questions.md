# 8/25 오전 외부 멘토링 질문 취합

**날짜**
2026년 8월 25일 (오전)

**참여자**
팀 전원 (파트별 개별 질문)

**진행 배경**
발급 파이프라인(Redis Stream → Lua → Kafka → DB) 배선이 아직 완성 전인 상태에서, 각자 담당 파트를 기준으로 멘토님께 확인받을 질문을 파트별로 취합했습니다. 팀원은 본인 파트 질문만 진행합니다.

---

## 박수빈 — Redis Lua / Stream Worker

1. Redis Lua에서 재고를 차감한 이후 Kafka 발행이나 최종 DB 저장이 실패한 경우, 즉시 재고를 복구하는 것이 적절할까요? 아니면 중복 발급 위험을 고려해 실패 보상 큐나 정합성 보정 작업으로 분리하는 편이 더 안전할까요?
2. 대량 쿠폰 이벤트에서 Redis Stream Worker 수와 배치 크기는 어떤 지표를 기준으로 조절하시나요? Pending 메시지 수, 처리 지연 시간, Redis 사용률, Kafka Lag, DB 처리량 중 실무에서 우선적으로 보는 지표가 궁금합니다.
3. 쿠폰 발급 실패 사유를 사용자에게 어디까지 구분해서 안내하는 것이 좋을까요?
4. NOGROUP 발생 시 메시지 유실을 막기 위해 Consumer Group을 `0-0`부터 다시 생성하고 있습니다. 이 경우 기존 메시지가 대량으로 재전달될 수 있는데, 실무에서도 유실 방지를 우선하여 `0-0`부터 복구하는지, 아니면 별도의 복구 기준이나 운영 정책을 두는지 궁금합니다.

## 박신형 — 쿠폰 상태·정합성

1. 정합성 배치가 불일치를 발견해도 지금은 리포트에 기록만 하고 아무것도 자동으로 고치지 않습니다. `VerificationDetail`에 "현재 상태와 이력이 다르다"까지는 남기는데, 그다음 누가 어떻게 고치는지는 설계에 아직 없습니다 — 실무에서는 이런 불일치가 발견되면 사람이 직접 SQL로 고치나요, 아니면 미리 복구용 스크립트나 관리자 API를 만들어두나요?
2. 정합성 검증 배치를 하루 한 번 도는 걸로 설계했는데, 실무에서는 이런 배치를 보통 얼마나 자주 돌리나요? 실시간 스트림으로 감지하는 곳도 있는지 궁금합니다.

## 이성집 — 선착순 신청 API / 멱등성 / 파이프라인 연결

1. Idempotency 상태가 "접수 성공" 시점에 고정되는 게 맞는지. Stream 적재만 성공하면 `IdempotencyKeyService.succeed()`가 곧바로 호출돼 `SUCCEEDED`로 기록됩니다. 이후 Lua/Kafka 단계에서 실제로는 재고 소진 등으로 실패하더라도, 이 레코드 상태는 그대로 `SUCCEEDED`로 남는데 — 최종 결과가 나온 뒤에 이 상태를 다시 갱신하는 경로가 설계에 필요한지 궁금합니다.
2. 로그 레벨과 순서검증 로그가 같이 묶여 있는 구조. 부하테스트 때 `logging.level.com.mycom.petcoupon.coupon`을 WARN으로 낮추면, 선착순 순서 검증용으로 넣은 `[ISSUE] 접수 ...` 로그도 같이 꺼집니다. 순서 검증 로그와 일반 디버그 로그를 지금처럼 같은 로거/레벨에 묶어둬도 되는지, 아니면 애초에 분리해서 설계했어야 하는지 확인받고 싶습니다.
3. WAITING 하나로 클라이언트가 판단할 수 있는 정보가 충분한지. 발급 요청을 보내면 성공이든 품절이든 일단 `WAITING`만 응답합니다. 클라이언트 입장에서 이 응답만 보고 "언제쯤 재조회하면 되는지", "이게 진짜 접수된 게 맞는지"를 판단할 수 있는 정보가 지금 응답 구조에 담겨 있는지 검토받고 싶습니다.

## 전송흔 - 스케줄러 / 관리자 API

1. 트래픽이 큰 시스템이라면 스케줄러 실행 자체를 한 인스턴스로 제한하는 방식과 여러 인스턴스가 실행하되 조건부 UPDATE로 멱등하게 처리하는 방식 중 어떤 쪽을 더 선호하는지도 궁금합니다.

## 정자비 — Kafka / Outbox

1. Kafka 발행이 실패하면 Redis 재고를 바로 복구하지 않고, Outbox 상태를 "재발행 필요"로 남겨서 다음 주기에 다시 발행을 시도하는 방식으로 가기로 했어요. Redis 재고를 먼저 복구하면 아직 남아있는 Outbox 이벤트가 나중에 정상 발행되면서 초과발급이 생길 수 있어서예요. 그런데 이 재발행이 계속 실패해서 끝내 성공을 못 하면 그때는 어떻게 처리하는 게 좋을까요? (그 시점엔 Redis 보상을 해야 하는지, 아니면 사람이 개입해야 하는지)
2. Consumer가 처리 도중(오프셋 커밋 전) 재시작되거나 리밸런싱되면 같은 이벤트가 다시 소비될 수 있는데, 지금은 `existsByRequestId` 체크 하나로만 중복 저장을 막고 있어요. 이 정도 방어면 충분한가요, 아니면 리밸런스 상황에서 추가로 신경 써야 할 게 있나요?
3. Kafka 발행 실패를 Outbox 재발행 poller가 다음 주기에 다시 재시도해주는 구조를 만들려고 해요. 이 경우 Kafka client 자체의 내부 재시도(retries, delivery.timeout.ms)는 짧게 잡아서 실패 판정을 빨리 내리고 Outbox 쪽 재시도에 맡기는 게 나을까요, 아니면 Kafka client 재시도도 충분히 유지해서 일시적인 네트워크 문제는 그 안에서 흡수하는 게 나을까요?

## 함세연 — 부하 테스트

1. 프로젝트 목표가 재고 10,000 / 요청 20,000인데, 재고는 고정하고 요청만 50,000까지 늘려서 경쟁률을 2:1에서 5:1로 높이는 단계를 추가했습니다. 경쟁이 심할수록 동시성 결함이 드러날 확률이 높다고 판단했는데, 이런 방식이 실제로 의미가 있을까요? 아니면 목표 규모에서 반복 횟수를 늘리는 게 더 나은가요?
2. 부하 테스트 후 발급 건수를 세서 정합성을 검증하는데, 비동기라 부하가 끝나도 저장이 진행 중입니다. 부족한 게 유실인지 처리 중인지 구분이 안 돼서, 1초마다 DB를 폴링해 건수가 더 안 늘어나는 걸 확인한 뒤에 세는 방식을 선택했습니다. 이 방식이 맞을까요? 실무에서는 "비동기 처리가 다 끝났다"를 어떻게 판정하나요?
3. AWS EC2 3대(k6 발생기 / 애플리케이션 / DB·Redis)로 나누려고 합니다. k6를 앱 서버에서 돌리면 CPU를 뺏어가고, 앱과 DB를 한 대에 두면 병목 판별이 안 될 것 같아서요. 이 정도 분리면 충분할까요? 그리고 실무에서 부하 테스트 결과를 신뢰하려면 환경 구성에서 뭘 더 통제해야 하나요?
